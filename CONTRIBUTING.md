# Работа с репозиторием

Короткая памятка по тому, что настроено в репозитории и как это обслуживать.

## Как вносить изменения

Ветка `main` защищена правилом репозитория: изменения приходят через pull
request, принудительный пуш и удаление ветки запрещены.

```bash
git switch -c имя-ветки
# правки
git add -A
git commit -m "что сделано"
git push -u origin имя-ветки
gh pr create --base main --fill
```

В GitHub Desktop то же самое: `Current Branch` → `New Branch`, коммит,
`Publish branch`, `Create Pull Request`.

У владельца репозитория есть исключение в правиле (bypass роли
`Repository admin`), поэтому он может публиковать изменения в `main` напрямую
из GitHub Desktop. Остальные участники идут через pull request.

## Автоматика версий

`.github/workflows/release.yml` срабатывает на каждое попадание изменений в
`main`: поднимает патч-версию в `pyproject.toml`, коммитит её и отправляет
обратно в `main`.

Важные свойства, которые легко нарушить правкой:

- **Workflow не трогает `README.md`.** Раньше он дописывал туда строку лога на
  каждом запуске, и README целиком состоял из этих строк. Возвращать не нужно:
  если понадобится журнал изменений, его место — отдельный `CHANGELOG.md`.
- **Пуш идёт под секретом `SOURCECRAFT_TOKEN`** и проходит защиту `main` через
  тот же bypass роли `Repository admin`, поэтому токен обязан принадлежать
  администратору репозитория. Встроенный `GITHUB_TOKEN` здесь не подходит:
  в список исключений правила нельзя добавить GitHub Actions.
- **`paths-ignore` и `[skip ci]`** защищают от бесконечного цикла — пуш под
  персональным токеном перезапускает workflow. Снимать их нельзя.

После каждого запуска бота `main` уходит вперёд на один коммит. Перед
следующей публикацией нужно подтянуть изменения: в GitHub Desktop это
`Pull origin`.

## Замена токена CI

Секрет `SOURCECRAFT_TOKEN` стоит держать узким: fine-grained токеном на один
этот репозиторий, а не классическим токеном на все репозитории владельца.

Делает владелец репозитория:

1. `github.com/settings/personal-access-tokens` → `Generate new token`
2. Repository access: **Only select repositories** → этот репозиторий
3. Permissions → Repository permissions → **Contents: Read and write**.
   Больше ничего не выдавать
4. Скопировать значение токена
5. `Settings` → `Secrets and variables` → `Actions` → `SOURCECRAFT_TOKEN` →
   `Update secret` → вставить новое значение
6. **Проверить:** отправить любое изменение в `main` и убедиться, что прогон
   во вкладке `Actions` зелёный
7. **Только после зелёного прогона** отозвать старый токен на
   `github.com/settings/tokens`

Порядок шагов 6 и 7 несущий. Если отозвать старый токен до проверки и новый
не заработает, бот встанет, а чинить придётся вслепую.

Перед шагом 7 стоит убедиться, что старый токен не прописан в других
проектах: классический токен действует на все репозитории владельца, и его
отзыв может тихо сломать что-то соседнее.

## Уборка веток после мержа

Постоянное решение — галка в настройках:
`Settings` → `General` → `Pull Requests` → **Automatically delete head
branches**. После неё ветка удаляется сама при каждом мерже.

Галка не убирает то, что накопилось раньше. Для этого есть
`scripts/cleanup-merged-branches.ps1`:

```powershell
.\scripts\cleanup-merged-branches.ps1          # показать, что будет удалено
.\scripts\cleanup-merged-branches.ps1 -Apply   # удалить
```

Без ключа `-Apply` скрипт только читает. Удаляются лишь ветки со смерженным
pull request: ветка по умолчанию, защищённая ветка, ветка с открытым pull
request и ветка вовсе без pull request не трогаются никогда — за последней
может стоять чья-то незаконченная работа.

Калибровка скрипта — `scripts/cleanup-merged-branches.Tests.ps1`. Она гоняет
настоящий скрипт на подставных данных, наружу не ходит и ничего не удаляет.
Запускать после любой правки скрипта:

```powershell
.\scripts\cleanup-merged-branches.Tests.ps1
```

## Что намеренно не в репозитории

`.gitignore` исключает `_pyautocad/` — библиотеку pyautocad для Python.
Исключение сделано по размеру, это не ошибка: библиотека ставится через `pip`,
а не хранится в репозитории. Правило действует на любой глубине, поэтому папка
с таким именем не попадёт в коммит и внутри вложенных каталогов.

Там же исключены `settings.json` и `chat_history.json` — настройки и история
конкретного пользователя.
